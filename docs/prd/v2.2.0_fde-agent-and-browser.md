```
C1  Given  신규 고객사
    When   FDE 와 온보딩 대화 15분

C4  Given  분석 허용 폴더 1개
    When   FDE 가 로컬 분석
    Then   그 폴더 밖 접근 시도 0건 · 쓰기 0건

C5  Given  과제 2개가 동시에 같은 사이트에 로그인
    When   브라우저 도구 사용
    Then   두 과제의 쿠키가 섞이지 않는다

C6  Given  에이전트가 결제 버튼을 누르려 함
    When   브라우저 도구 호출
    Then   승인 전에는 실행되지 않는다

    Then   FDE 가 원인과 수정안 1건을 웹에 올린다

    When   고객이 채널에 질문을 보냄
    Then   임원(Chief) 스레드가 생기고(출처 = slack) 웹 '메신저' 화면에 그 대화가 보인다

C9  Given  임원이 답장 초안을 만듦
    When   승인 전
    Then   채널로 아무것도 나가지 않는다 — 승인 후 1회 발송, 감사 기록에 남는다

C10 Given  Gmail 이 연결됨
    When   새 메일 도착
    Then   스레드로 정리되고, 답장은 C9 와 같이 승인 후 발송된다

C11 Given  카카오톡 채널 챗봇 웹훅
    When   서명이 틀린 요청
```

### 4.1 아키텍처 · 구조 (system-architect)

#### I1. FDE 가 도는 자리
| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **FDE = 별도 thread 의 에이전트.** 업무 thread(Chief 진입)와 섞지 않는다. 온보딩 · 개선 주기는 cron/goal 이 FDE thread 를 띄운다. 웹에는 FDE 전용 대화 채널 | 회사 정의를 고치는 대화와 업무 대화가 분리된다 · 주기 실행을 기존 cron/goal 로 띄운다 | 웹에 채널이 하나 더 생긴다 |
| ⓑ | 업무 thread 안에서 Chief 가 FDE 를 하위 에이전트로 부른다 | 진입점이 하나 | 업무 맥락과 정의 수정 맥락이 한 thread 에 섞인다 |
- **채택:** ⓐ
- **선택 근거:** FDE = org 팀의 일원이자 1급 역할(결정 27 · 40) · 온보딩부터 고객과 대화(결정 27 ⑴)
- **기각 이유:** ⓑ — 회사 정의를 바꾸는 대화가 업무 이력에 묻혀 승인 · 감사 단위가 흐려진다
- **반증 조건:** 사용자가 FDE 채널을 따로 찾지 않아 온보딩 · 수정안이 방치되는 것이 관측되면 다시 연다
- **부작용:** 웹 채널 1개 추가(v2.1.0 웹 표면에 의존) — 큰 부작용 없음

- **부작용:** 없음 — 커밋 ↔ 제안 id 대응만 지키면 된다

#### I16. Google Calendar 동기화 · 일정 도구 (결정 60)
| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **읽기 먼저** — Google Calendar API(OAuth, 캘린더 읽기 범위)로 가져와 `core.db` `calendar` 에 `source` · `source_id` 를 단 읽기 전용 항목으로 둔다 · 증분 동기화(sync token) + push 채널, 끊기면 주기 동기화 | 원본 손상 위험 0 · 범위가 작은 OAuth 동의 · v2.1 의 권한 · 404 · 에이전트 읽기 단계를 그대로 재사용 | 고객이 SoloSquad 에서 고치고 싶어 한다(→ 양방향 단계) |
| ⓑ | 처음부터 양방향 | 한 곳에서 다 고침 | 충돌 규칙(F11) · 반복 일정 예외 · 지운 것 전파 · 쓰기 범위 OAuth 동의 — 실수 한 번이 고객 원본을 망친다 |
| ⓒ | 가져오지 않고 화면에서 Google 을 겹쳐 보이기만 | 저장 없음 | 에이전트가 읽을 수 없다 · 오프라인 · 필터 · 할 일 연결 불가 |
- **채택:** ⓐ(F9) — 양방향은 F11 확정 뒤 같은 출처 표시 위에 쓰기를 더한다.
- **에이전트 도구:** MCP `calendar.read(from, to)` → 엔진 내부에서 `GET /api/calendar/agent-view`(v2.1 에 있음 — 엔진 토큰 = 누구든, 사람 = 본인만, 그 밖 404). 개인 = 단계대로, 업무 = 그 사업의 항목(같은 범위 판정 `role_in`). 가져온 항목에도 같은 규칙.
- **선택 근거:** 결정 60 ⒝ ⒟ · 결정 59(연결 틀) · 결정 51(밖으로 나가는 쓰기 = 승인)
- **기각 이유:** ⓑ — 위험이 먼저 온다. ⓒ — 에이전트가 못 읽는다.
- **반증 조건:** 파일럿 고객 다수가 SoloSquad 를 일정의 정본으로 쓰기 시작하면 양방향(ⓑ)을 앞당긴다.
- **부작용:** `cal_items` 에 `source` · `source_id` · `synced` 열(새 마이그레이션 판) · 연결 종류 '일정' · 토큰 갱신 실패 = 연결 상태 경고(메신저와 같은 화면).
