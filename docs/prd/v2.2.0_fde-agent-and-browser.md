## 4. 인수 조건

- Given 신규 고객사 / When FDE 와 온보딩 대화 15분 / Then org 패키지 1개가 깔리고 첫 워크플로 1개가 웹에 켜진다
- Given FDE 가 스킬 수정을 제안 / When 사장님이 거절 / Then 정의 파일은 바뀌지 않는다
- Given 승인 후 적용된 변경 / When 롤백 명령 / Then 직전 버전으로 돌아가고 커밋 이력이 남는다
- Given 분석 허용 폴더 1개 / When FDE 가 로컬 분석 / Then 그 폴더 밖 접근 시도 0건 · 쓰기 0건
- Given 과제 2개가 동시에 같은 사이트에 로그인 / When 브라우저 도구 사용 / Then 두 과제의 쿠키가 섞이지 않는다
- Given 에이전트가 결제 버튼을 누르려 함 / When 브라우저 도구 호출 / Then 승인 전에는 실행되지 않는다
- Given 실패 · 승인 거절이 임계치를 넘음 / When 개선 주기 / Then FDE 가 원인과 수정안 1건을 웹에 올린다

## 5. 구현 방법

> R9 — 착수 시 담당 에이전트가 아래 초안을 리뷰해 확정한다(R5). 지금은 방향과 대안까지만.

### 5.1 아키텍처 · 구조 (system-architect)
- **FDE = 별도 thread 의 에이전트.** 업무 thread(Chief 진입)와 섞지 않는다. 온보딩 · 개선 주기는 cron/goal 이 FDE thread 를 띄운다. 웹에는 FDE 전용 대화 채널.
- **쓰기 경로 하나** — FDE 의 모든 변경은 "변경 제안" 객체(대상 파일 · diff · 이유) → 승인 → 고객사 리포 커밋. FDE 가 파일을 직접 쓰는 도구는 주지 않는다.
- **브라우저 = 도구 서버** — Chromium 은 사무실 인스턴스가 소유하는 MCP 서버 하나(결정 25). 하네스마다 따로 붙이지 않는다.
- 대안: FDE 가 파일을 직접 쓰고 사후 리뷰 ⓑ — 기각(롤백 · 감사가 약해진다).

### 5.2 설계 (각 구현 담당)
- **변경 제안** — `propose_change(path, new_content, reason)` MCP 도구 → 승인 대기(interrupt) → 승인 시 엔진이 커밋. 대상 경로는 org 범위로 검사, core 경로는 오너 승인 플래그 필요.
- **로컬 분석** — 허용 폴더 목록(`local.yaml`) 밖 접근은 도구 단에서 거부. 엑셀 · CSV 는 pandas 로 요약 후 에이전트에 전달(원본 전체를 프롬프트에 넣지 않는다).
- **브라우저** — 과제마다 `BrowserContext`, 쿠키는 데이터 폴더 암호화 저장. 결제 · 제출 패턴(도메인별 규칙)은 가드 규칙으로 승인 필요.
- **개선 주기** — 가계부 · run 실패 · 승인 거절을 집계하는 분석 함수 → FDE 프롬프트 입력.

### 5.3 데이터 (data-engineer)
- 변경 제안 기록(`proposals`: id · 경로 · diff · 이유 · 상태 · 승인자) — 데이터 폴더.
- 분석 결과는 고객사 서버 안에만. v2.3.0 의 에이전시 전송은 메타데이터 요약으로 별도 생성.
- 브라우저 쿠키: 사무실 · 과제 키로 분리 저장, 과제 종료 시 과제 컨텍스트 삭제(로그인 유지가 필요한 사이트는 사무실 공용 프로필로 명시 승격).

### 5.4 보안 · 권한 (security)
- FDE 변경 범위 집행은 도구 단(경로 검사) + 커밋 단(리포 밖 쓰기 불가) 이중.
- 브라우저 자동화가 금지된 사이트 목록과 주의를 org 패키지에 둔다.

### 5.5 작업 분할 · 담당
| 작업 | 담당 |
|---|---|
| FDE 에이전트 정의 · 온보딩 대화 | product-manager · (org 패키지) |
| 변경 제안 도구 · 승인 · 커밋 · 롤백 | backend · security |
| 로컬 분석 도구 · 요약 | data-engineer · data-analyst |
