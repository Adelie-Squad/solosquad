- **이 버전이 맡는 조각:** 엔진 · 웹 · FDE · 에이전시 연결(v2.0~v2.3)과 결이 다른 **운영(deploy/health) 축**. 두 조각 —
  - **조각 A(정합성 fix + 승격)** — 배포 자산에 남은 죽은 명령 정리 + **Railway 를 기본 클라우드로 승격**(원클릭 템플릿 · 요금 투명성 · 비용 절감 가이드).
  - **조각 B(신규 ops)** — **봇 세션 health → 메신저 알림.** 봇과 다른 failure domain 의 watchdog 가 사망을 통지. 포함 여부 = D1.
  - 결정 16 · 33 이후 추가 몫: **메신저 재도입 · 클라우드 접속 인증(M18 잔여) · 헤드리스 구독 로그인(M25 ⓑ) · 헤드리스 브라우저(M27 ⓓ)** — 범위 정의는 D7.
- **이 버전이 끝나면** 맥을 끄거나 자리를 비워도 클라우드의 봇과 메신저로 24/7 일할 수 있고, 봇이 **"안정적으로 뜨고, 죽으면 알린다"(healthy)** 까지 닿는다. repo 작업이 가능한 *완전 기능* 봇(`healthy → functional`)은 후속 minor(§3.2).

- **기존 자산의 결함** —
  - `manual/cloud-deployment.md` 는 Railway 를 **Option B(얇음)** 로만 두고 1순위는 VPS. Railway start command 가 `npm run build && node dist/... schedule` — **죽은 `schedule`**(v1.3.3 에서 `cron` 으로 교체, CHANGELOG `[1.3.3]`).

**가치 문장(누가 · 왜 · 어떻게 · 어떤 가치)**

> 클라우드에 봇을 두려는 비-개발 성향 원격 운영자가(누가), 배포가 어렵고 요금이 무섭고 봇이 조용히 죽을까 두려워(왜), **Railway 1순위 가이드(원클릭 지향 + 요금/비용 투명) + 봇과 별개 watchdog 의 메신저 사망 통지**로(어떻게), **"쉽게 띄우고, 얼마 나올지 알고, 죽으면 바로 안다"는 예측가능성**을 얻는다(어떤 가치).

### 3.2 이번 버전 비포함

- **클라우드 *기능적* 온보딩(별도 minor)** — **W3 repo remote-clone 등록**(D5) · **W2 완전 자동 인증**(env-var API 키 또는 비대화형 로그인, D4) · **비대화형 `init --yes`**(W1, D2). 이 셋이 모여야 `healthy → functional`(repo 작업 가능) 완성.
- **GCP/GCE** — 이전 초안의 기본안이었으나 Railway 로 교체(후순위로도 추가하지 않음, I1).
- **Telegram/Slack 어댑터(messenger 추상화)** · **웹 setup UI** — 별도 minor(§1 배경 표의 간극).
- **serverless-sleep 비용 절감** — a안(슬래시-wake) · b안(도어맨/워커 분리) 둘 다 이 버전 밖(I6 후속 카드, D6). 이 버전은 항상-켜둠 + RAM cap 으로만 대응.
- **메신저 원격 재시작**(사용자 명시 비-우선) — 알림까지만, 재시작은 `Restart=always`.
- **서비스 전체 다운 알림**(I2 Approach A 한계) — 외부 uptime 2차는 문서 옵션만.
- **Chief 세션 좀비**(프로세스 생존 · 세션 wedge) 감지 — heartbeat 가 턴-독립이라 미포착, 후속.

### 3.3 영구 비범위

- **샤딩 · K8s** — 수만 길드 규모에만 해당(Discord 봇 배포 레퍼런스 공통 정설, §8 참고). 서버는 고객사마다 하나(결정 18)라 대상 아님.

### 3.4 인수 조건

```
C1  Given  Railway 에 bot + cron 두 서비스가 떠 있고 watchdog 활성
    When   bot 프로세스가 SIGKILL(하드킬)로 사망
    Then   ≤120s 내 command/status 채널에 "🔴 봇 무응답(heartbeat N s stale)" 이 1회 post 된다

C2  Given  bot 이 정상적으로 5분 이상 걸리는 Chief 턴을 처리 중
    When   그 5분 동안
    Then   watchdog 는 사망 알림을 보내지 않는다(heartbeat 독립 타이머가 계속 기록)

C3  Given  사용자가 "Deploy on Railway" 로 컨테이너를 띄우고 railway ssh 로 접속해 solosquad init 완료
    When   docker/Railway 스택이 기동
    Then   bot · cron 두 서비스가 running 이고 cron 서비스가 'unknown command schedule' 로 죽지 않는다

C4  Given  bot 이 부팅 또는 graceful drain 에 들어감
    When   부팅 heartbeat 기록 직후 / drain 핸들러 진입 시
    Then   같은 채널에 "🟢 online" / "🟡 draining" 이 best-effort 로 post 된다

C5  Given  클라우드 bot 의 Claude 세션이 로그아웃되어 AuthExpiredError 가 발생
    When   사용자가 명령을 보내지 않은 상태에서도
    Then   announce 채널에 "🔐 Claude 로그아웃 — railway ssh 후 claude login" 이 능동 push 된다

C6  Given  railway ssh 에서 claude login 을 마쳐 토큰(~/.claude.json + ~/.claude)이 영구 볼륨에 있음
    When   컨테이너가 재시작
    Then   재로그인 없이 토큰이 유지된다

C7  Given  실 Railway 배포 1회와 그 청구서
    When   요금 투명성 절의 수치(선불 $5 · 사용량 과금 · 메모리 주도)와 비용 절감 env 를 청구서와 대조
    Then   문서 수치가 실 청구와 일치한다
```

## 4. 구현 방법

> R9 · R5 — 아래 후보 · 채택은 이관 전 원문의 approach 비교를 옮긴 **초안**이다. 착수 시 담당 에이전트(cloud-admin · backend · security · qa)가 v2 런타임(D7) 기준으로 리뷰해 확정한다. 리뷰 전 binding 아님.

### 4.1 아키텍처 · 구조

**As-Is 코드 감사 — 클라우드 전환의 숨은 벽(R3 · R4, feasibility; v1 TS 코드 기준).** 로컬(맥) 모델은 **볼륨 마운트가 설정 · 인증 · repo 를 공짜로** 준다. 클라우드엔 호스트가 없어 이 셋을 새로 만들어야 한다. 코드 확인 결과 세 벽이 같은 모양이며, 그중 둘(W2 · W3)은 이 PRD 가 처음 드러냈다.

| 벽 | 현재 코드(로컬 전용) | 클라우드 함의 |
|---|---|---|
| **(W1) 대화형 init** | `solosquad init` 전면 인터랙티브(`src/cli/init.ts`) | 비대화형 부재(§1 배경 표) |
| **(W2) Claude 인증** | OAuth 토큰 `~/.claude.json` 만 사용. 로그인 = `claude login`(브라우저 OAuth, `init.ts:75-86`). 중간 로그아웃 시 `AuthExpiredError` → *"호스트에서 `claude login` 하라"* 고 답할 뿐 **자동 재로그인 없음**(`index.ts:347-351`). API 키는 봇 동작에 미사용(revoke 체크리스트에서만 식별용) | 컨테이너엔 **브라우저도, 곁의 사용자도 없음.** 초기 · 중간 재로그인 둘 다 `railway ssh` + `claude login` 코드-페이스트 필요(headless 지원 **검증 필요**). 토큰은 **영구 볼륨**에 둬야 재시작에 유지 |
| **(W3) repo 경로 참조** | repo 를 **절대 로컬 경로**로 등록(`<org>/repositories/<slug>.yaml` 의 `path:`, `init.ts:254`). 런타임 `resolveRepoCwd()` → Claude `--add-dir <절대경로>`(`chief-runner.ts:148-172`). **등록 시 git URL 거부**(로컬 경로만, `init.ts:178-216`). compose 는 로컬 트리를 `${REPOS_BASE_PATH}:/repos` 로 마운트 | 클라우드엔 `/Users/.../` 경로 자체가 없음. registry 가 `remote_url` 은 저장하므로 **remote 에서 clone → 볼륨 등록**이 정석. 단 init 이 URL 등록을 못 함 → 신규 코드 필요(D5) |

결론(스코프 갈림) — W2 · W3 는 *"프로세스가 떠도 기능하지 못함"* 의 원인(`healthy ≠ functional`). 이 버전은 **"안정적으로 뜨고, 죽으면 알린다"**(W1 은 `railway ssh` 로 우회)까지, W2 의 완전 자동 경로 · W3 는 별도 minor. 단 **W2 최소선(토큰 볼륨 영속 + auth-expired 메신저 통지)** 은 조각 B 와 시너지라 포함.

**구조(To-Be)** — Railway 위 **bot + cron 2서비스**(compose 와 동형, YAGPDB 의 web/bot/feed 프로세스 분리 선례) ↔ Discord ↔ Anthropic. 알림 주체 = cron 데몬(봇과 다른 failure domain). 상태(워크스페이스 · 토큰 · heartbeat)는 **컨테이너 영구 볼륨**. 다이어그램은 §4.5 M2 디자인 작업.

| ⓐ | **Railway** — GitHub 연동/템플릿 · Config as Code(`railway.toml`) · Deploy 버튼 | 서버 관리 없음 · 원클릭 템플릿 선례(Discord Tickets) · 2서비스 구성 자연스러움 | $5 선불 + 사용량 과금(bill shock) · always-on RAM 이 바닥값 |
| ⓑ | GCP/GCE (이전 초안 기본안) | 범용 클라우드 | VM 관리 필요 — "서버 관리 없이"라는 진입 마찰 목표와 반대 |
| ⓒ | VPS + systemd (기존 cloud-deployment 1순위) | 비용 예측 쉬움 · `Restart=always` | 서버 관리 · SSH 운영이 사용자 몫 |
| ⓓ | Fly / ECS (Docker) | 컨테이너 표준 · 포터블 | `[보강 필요: 1순위에서 밀린 사유 — 원문은 "후순위 유지"만 기록]` |
| ⓔ | Cloudflare(결정 39 PoC 경로) | v2 PoC 와 같은 배포 환경 | Workers · Pages 는 Python 엔진 · CLI 하네스를 직접 돌리지 못함(결정 39 · M33) |

- **채택:** ⓐ Railway = Option 1(추천), ⓒ ⓓ 는 후순위 유지(포터블 수혜 대상).
- **선택 근거:** 서버 관리 없이 GitHub 연동/템플릿으로 가장 빨리 띄운다(진입 마찰 KR). 성숙 Discord 봇 프로젝트의 공통 정설 = *단일 컨테이너 항상-켜둠 · env-var 토큰 · 상태는 외부(볼륨/DB) · 원클릭 버튼* — Discord Tickets 의 Railway 원클릭 버튼 · Modmail 의 Heroku 버튼 선례(§8 참고). 참고 스크립트의 요금 구조 · 메모리 cap 재사용 가능.
- **기각 이유:** ⓑ — Railway 로 교체, 후순위로도 추가 안 함 · ⓒ — 서버 관리 부담으로 1순위에서 내림(후순위 유지) · ⓓ — 후순위 유지 `[보강 필요]` · ⓔ — 엔진 실행 불가(M33).
- **반증 조건:** D7 재정의에서 고객사 클라우드 사무실(결정 40)의 엔진 위치가 M33 권장(창업자 상시 머신 + Cloudflare Tunnel) 또는 컨테이너 호스트로 확정되고 Railway 가 그 구성에 맞지 않으면 다시 연다.
- **부작용:** always-on RAM 비용 · 사용량 과금 bill shock(→ §5 K4) · Railway 고유 기능(템플릿 · `railway ssh`)에 온보딩이 묶임(→ §5 K5).

#### I2. 봇 사망 알림 구조

**제약** — 죽은 봇은 스스로 못 알린다 → 알림 주체 = 봇과 **다른 failure domain 의 살아있는 프로세스**. compose/Railway 는 bot · cron 을 별도 서비스로 분리하므로 이를 활용한다. Discord 는 항상-켜둠이라 sleep 과 충돌이 없다 — heartbeat 정지 = 진짜 사망.

| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **Heartbeat + watchdog(cron 데몬 내장) + boot/drain announce** — 봇이 `<ws>/.solosquad/bot.heartbeat` 에 턴-독립 타이머로 timestamp 기록, 상시 · 별도인 cron 데몬이 staleness > 임계 시 메신저로 `🔴 봇 무응답(heartbeat N s stale)` post. 부팅 `🟢 online`, drain `🟡 draining` best-effort | 하드킬 포착 ✅(독립 프로세스) · **대화하는 메신저에 직접 도달** ✅ · 신규 ingress/보안면 없음 · 포터블(Railway/Docker/VPS) ✅ | 서비스 전체 다운 미포착(둘 다 죽음) |
| ⓑ | Railway/외부 uptime 모니터 — 봇 `/healthz` HTTP → healthcheck/외부 uptime → 알림 채널 | 하드킬 포착 ✅ · 서비스 전체 다운 포착 ✅ | 메신저 도달 ❌(보통 email/webhook) · HTTP 공개 = 신규 보안면 · 플랫폼별 |
| ⓒ | process-manager OnFailure 훅 — systemd `OnFailure=`(VPS) / Docker healthcheck + 사이드카 | 메신저 도달 ✅ · 신규 ingress 없음 | 하드킬 포착 ⚠️ · systemd 종속 · 서비스 전체 다운 미포착 |

- **채택:** ⓐ. ⓑ 는 **보완 레이어로 문서화만**(서비스 전체 다운은 Railway 자체 알림/외부 uptime 2차 — 구현 비대상).
- **선택 근거:** 메신저 직접 도달 · 포터블 · 신규 보안면 0 · 상시 cron 데몬 재사용(V/U/V/F Viable). heartbeat 는 기존 `src/util/bot-pidfile.ts` 의 `isProcessAlive`/PID 패턴과 동형(Feasible).
- **기각 이유:** ⓑ — 대화 채널에 닿지 않고 HTTP 공개면을 새로 연다 · ⓒ — 하드킬 포착이 불확실하고 systemd 에 묶여 Railway 에서 쓸 수 없다.
- **반증 조건:** watchdog 가 정상 장시간 Chief 턴을 사망으로 오인해 false 알림이 나고, 튜닝(I4)으로 0 에 수렴하지 않으면 ⓐ 기각 → ⓒ 로 후퇴.
- **부작용:** 서비스 전체 다운 미포착(→ §5 K2) · 프로세스는 살았지만 세션이 멈춘 좀비 미포착(→ §5 K3).

#### I3. watchdog 호스트

| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **cron 데몬(`cron start`) 내장** | 상시 · 별도 프로세스 재사용 → 신규 인프라 0 | bot-only 배포(cron 미기동)면 watchdog 부재 |
| ⓑ | 전용 `solosquad watchdog` 프로세스 | cron 기동 여부와 무관 | 서비스 · 명령 하나 추가(배포 · 문서 · 테스트 증가) |

- **채택(잠정):** ⓐ — D3 결정으로 확정.
- **선택 근거:** Railway 템플릿이 bot + cron 두 서비스를 기본 포함하면 bot-only 배포 문제가 자연 해소된다(원문 결정 3 메모).
- **기각 이유:** ⓑ — 템플릿이 2서비스를 강제하면 얻는 것 없이 프로세스만 늘어난다.
- **반증 조건:** 템플릿이 2서비스를 기본 포함하지 못하거나, bot-only 배포 사용자가 실재하면 ⓑ 또는 "클라우드는 bot + cron 동반 기동" 가이드 박제.
- **부작용:** cron 데몬 장애 = 알림 장애(cron 이 죽으면 bot 사망도 모름) → §5 K8.

### 4.2 설계

- **heartbeat 모듈** — `src/util/bot-heartbeat.ts`: write / read / staleness(PID 유틸 동형). 봇 `src/bot/index.ts` 가 부팅 시 heartbeat 시작 + `🟢 online`, drain 핸들러에서 `🟡 draining`. watchdog 는 staleness 판정 시 1회만 post(C1). *(경로는 v1 TS — D7-1.)*
- **auth_expired 능동 통지(W2 최소선)** — `chief-runner.ts` 가 이미 `AuthExpiredError` 를 던지나(`L717-724`) 현재는 *사용자가 명령을 보낼 때만* 답으로 알린다. 클라우드는 곁에 아무도 없으므로 **announce 경로에 `🔐 Claude 로그아웃 — railway ssh 후 claude login` 능동 push** 를 추가(boot/drain announce 와 같은 채널, C5). 재로그인 자체는 여전히 `railway ssh`. 작음(에러 클래스 · 채널 재사용).

#### I4. heartbeat 기록 타이머

| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **턴 루프와 독립된 `setInterval`** — 주기 30s, 임계 = 주기×3 + 여유 = 120s | 턴이 길어도 계속 기록 → 장시간 턴 오경보 0(C2) | 프로세스는 살고 세션만 멈춘 좀비를 못 잡는다 |
| ⓑ | 턴 루프 안에서 기록(턴 진행 = 생존 신호) | 세션 wedge 까지 포착 가능 | 5분 이상 정상 턴에서 오경보 — Usable 가정(오경보 0)과 정면 충돌 |

- **채택:** ⓐ.
- **선택 근거:** 원문 반증 조건의 가드 — *"heartbeat 는 턴 루프와 독립 setInterval, 임계 = 주기×3 + 여유(30s → 120s)"*. MTTA ≤ 120s 목표와 같은 수치.
- **기각 이유:** ⓑ — 정상 장시간 Chief 턴을 사망으로 오인(Hard gate 위반).
- **반증 조건:** 4주 운영에서 false-down 이 0 이 아니면 주기 · 임계 재튜닝, 그래도 안 되면 I2 를 ⓒ 로.
- **부작용:** 좀비 세션 미포착(→ §5 K3, 후속).

#### I5. 원클릭 온보딩 간극 메우기

스크립트의 "터미널 없이 8분"은 **비대화형 온보딩**이 전제다. SoloSquad `init` 은 인터랙티브다.

| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **`railway.toml` 템플릿 + 배포 후 `railway ssh` → `solosquad init`** — 버튼 → 컨테이너 기동 → 사용자가 `railway ssh` 로 컨테이너 안에 접속해 `init` 1회(대화형 그대로) → env 에 토큰 | 작업량 **소**(템플릿 파일 + 문서, init 코드 무변경) · patch 적합 ✅ | 스크립트 재현도 중(원클릭 후 1스텝 남음) · 사용자에 `railway ssh` 1스텝 요구 |
| ⓑ | 비대화형 env-var `solosquad init --yes` — 템플릿 + env-var(DISCORD_TOKEN · OWNER_* · 핸들)만으로 init 자동 완료, 쉘 불필요 | 스크립트 재현도 고(진짜 원클릭) | 작업량 **대** — init 전체를 env-var 주입 · 검증 · idempotent 로 재설계(인터랙티브 분기 다수) · ⚠️ 사실상 minor 기능 · init 회귀면 모든 신규 온보딩이 깨진다 |
| ⓒ | `railway run` 으로 init | 쉘 접속 불필요 | *내 노트북에서* 실행 → 워크스페이스 파일이 로컬에 생겨 컨테이너 볼륨에 남지 않음 |

- **채택:** ⓐ(D2 권장안). ⓑ 는 별도 minor — messenger 추상화 · 웹 setup UI 와 함께 묶는 게 자연스럽다.
- **선택 근거:** 버전 규모에 맞고 init 코드 리스크 0. `railway ssh` 인 이유 — init 이 만드는 워크스페이스(`agents/` · `.solosquad/`)가 **컨테이너 영구 볼륨**에 생겨야 재기동에도 유지된다.
- **기각 이유:** ⓑ — 규모 초과 · 회귀 시 전 온보딩 파손 · ⓒ — 파일이 로컬에 생겨 부적합.
- **반증 조건:** `railway ssh` 1스텝이 비-개발 사용자에게도 충분히 쉬우면 ⓑ 불요. 그 1스텝조차 마찰이 크다는 dogfood 근거가 나오면 ⓑ 로 승격.
- **부작용:** 사용자 마찰 1스텝(→ §5 K5) · W3 미해결로 healthy 이지만 functional 아님(→ §5 K7). *(v2 에서 init 은 Python CLI — D7-1.)*

**사용자 여정 — Railway 배포 step-by-step(ⓐ 기준).** 각 단계가 이 버전 코드로 닿는지 박제(= dogfood 때 막히는 지점 사전 노출).

| 단계 | 사용자 행동 | 이 버전 도달 |
|---|---|---|
| **0. 사전** | Discord 봇 토큰 발급 · **product repo 를 remote(GitHub)에 push**(클라우드는 remote 에서 받음, W3) · Railway 가입 | — |

#### I6. 비용 절감 방식

| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **항상-켜둠 + 메모리 cap** — env `NODE_OPTIONS=--max-old-space-size=1024` 로 힙 상한 | 메모리 과금 억제(실측상 메모리가 주 비용) · 스크립트 재사용 · 코드 무변경 | 바닥 비용 남음(예상 월 ~$8–20, 워크로드 의존) |
| ⓑ | Railway serverless/sleep 그대로 | 최대 절감 | **Discord 에서 성립 안 함** — gateway WS 는 sleep 시 메시지 수신 · 웨이크 불가. Railway sleep 은 *인바운드 HTTP 부재 ~10분* 에 트리거되는데 Discord 봇엔 인바운드가 없어 깨울 통로 자체가 없다 |
| ⓒ | (후속 카드) a안 슬래시-wake — Discord Interactions Endpoint(HTTP)로 `/sq <내용>` 슬래시 커맨드를 wake 진입점 삼아 인바운드 POST 로 기동 → gateway 연결 후 자연어 대화 | sleep 살림 | 첫 wake 콜드부팅이 **3초 ack 데드라인** 초과로 실패 가능 · 자는 중 보낸 평범한 메시지 유실 |
| ⓓ | (후속 카드) b안 도어맨/워커 분리 — 경량 항상-켜둠 프로세스가 gateway WS 만 들고(싼 RAM), 무거운 에이전트 워커는 sleep → 메시지 시 깨움 | 자연어 UX 무손실 | 구조 변경(≈ cloud-deployment Option E, Agent SDK + Sandbox 분리) — 규모 초과 |

- **채택:** ⓐ. ⓒ ⓓ 는 이 버전 밖 후속 카드(D6 — 비용이 실제로 아플 때).
- **선택 근거:** 참고 스크립트의 메모리 cap 재사용 · Discord 항상-켜둠 성질(§1 배경 표).
- **기각 이유:** ⓑ — 깨울 통로 없음 · ⓒ — 3초 ack · 메시지 유실 · ⓓ — 버전 규모 초과.
- **반증 조건:** 실 청구서(C7)에서 always-on 비용이 사용자 수용선을 넘으면 D6 를 연다.
- **부작용:** 힙 상한이 너무 낮으면 장시간 작업 중 OOM 가능 — `[보강 필요: 1024MB 상한의 근거 실측 · 헤드리스 Chromium(M27 ⓓ) 동거 시 메모리 요건]` → §5 K10. *(`NODE_OPTIONS` 는 Node 전용 — Python 엔진 기준 재정의 D7-1.)*

| Node 베이스 | `node:20-slim`(CI 가 Node20 매트릭스를 제거 — 불일치) | **`node:22-slim`**(active LTS), `engines ">=20"` 호환 |

- **채택:** To-Be 그대로. **검토한 대안 없음** — 폐기된 명령 · CI 와 어긋난 베이스 이미지의 정합 수정이라 선택지가 없다(`cron start` = 구 `schedule`, `src/cli/index.ts` L123-132).
- **선택 근거:** CHANGELOG `[1.3.3]`(schedule → cron 출처) · CI Node 매트릭스.
- **반증 조건:** D7 에서 v2 Python CLI 로 기동 명령 · 베이스 이미지가 바뀌면 이 결정 자체가 대체된다.
- **부작용:** 없음 — 이미 죽어 있던 명령을 살리는 수정이라 기존 사용자 동작을 바꾸지 않는다.

**인수 조건별 확인 수단**

| 조건 | 확인 수단 | 통과 게이트 |
|---|---|---|
| C1 | 실기 — 강제 `kill -9` 후 알림 도착 시간 실측 + 자동 회귀(stale → 알림 1회) | ≤120s · 1회 |

| C7 | 사람 리뷰 — 실 Railway 1회 청구서 대조 | 요금 절 수치 일치(Hard gate) |

**성공 기준**

- ① 신규 Railway 배포 소요 ≤ **15분** — 측정 범위 = **"프로세스 healthy 까지"**(템플릿 + `railway ssh` + `claude login` + `init`, dogfood 실측). repo 작업 가능한 완전 기능 봇(W3 remote-clone)까지의 시간은 후속 minor 지표로 이연(`healthy ≠ functional`).
- ② **MTTA**(봇 사망 → 메신저 알림) ≤ **120s**.
- ③ watchdog **false-down = 0**(장시간 턴 포함 **4주**).
- ④ 요금 절 수치가 실 청구서와 일치(검증 1회).
- **선행 지표:** 강제 `kill -9` 후 알림 실측 · false-down 카운트 · dogfood 배포 타임.
- **후행 지표:** "봇 죽은 줄 몰랐다" · "요금 폭탄" 리포트 0 수렴.

**R6 분기 — "변경 surface 에 LLM/에이전트가 들어가나?" → No.** 이 버전 surface(railway 템플릿 · compose · Dockerfile · 배포/요금 문서 · heartbeat · staleness 폴링 · announce)는 전부 결정론적 ops · infra. 봇이 감싸는 에이전트의 동작 · 프롬프트 · 허용 답변 범위는 바뀌지 않는다 → AI 부록 4칸 비활성. *(D7 재정의로 메신저 대화 · 헤드리스 브라우저 범위가 정해지면 다시 판정.)*
