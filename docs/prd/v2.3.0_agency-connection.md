### 3.4 인수 조건

```
C1  Given  새 컴퓨터
    When   curl … | sh (또는 irm … | iex)
    Then   Python 사전 설치 없이 설치되고 해시가 다르면 중단된다

C2  Given  에이전시가 새 코어를 릴리스
    When   고객사 FDE 가 받음
    Then   그 고객사 기준 설명과 적용 · 보류 · 건너뛰기가 웹에 뜨고,
           사용자가 고르기 전에는 코어가 바뀌지 않는다

C3  Given  org 에 커스텀 스킬 2개 · core/custom/hooks/ 훅 1개
    When   코어 업데이트 적용
    Then   커스텀이 그대로 동작하고, 회귀 점검이 실패하면 직전 엔진으로 자동 복귀한다

C4  Given  같은 컴퓨터의 고객사 A 는 적용 · B 는 보류
    When   둘 다 구동
    Then   A 는 새 엔진, B 는 이전 엔진으로 돈다

C5  Given  셀프 사용자가 측정에 동의하지 않음
    When   24시간 구동
    Then   에이전시로 나가는 요청 0건

C6  Given  관리형 설치본 3곳
    When   에이전시 화면
    Then   상태 · 코어 버전 · 최근 오류가 가명 ID 로 보이고 고객사 이름은 에이전시 어디에도 없다

C7  Given  고객사 FDE 의 승격 후보
    When   전송
    Then   후보에 고객사 정보가 없고 에이전시 FDE 의 판단이 채널로 돌아온다

C8  Given  고객사 FDE 의 자유 텍스트 질문
    When   전송
    Then   비식별 필터와 사장님 확인을 거친 내용만 나가고 나간 내역 에 남는다
```

### 4.1 아키텍처 · 구조 (system-architect)

```
 에이전시                                         고객사 머신(설치본마다)
 GitHub Releases(코어 · org 패키지 · 해시)  ──▶   설치기 → ~/.solosquad/engines/<버전>/
 설치 스크립트 도메인(버전 핀)                      인스턴스 ─ 업데이트 확인 → FDE 설명 → 사용자 결정
 수신 서버(Workers + D1, A3)  ◀── 가명 요약 · 후보 · 메시지 ──  나간 내역(웹)
 에이전시 FDE · 관할 화면 ── PR ──▶ SoloSquad 저장소 / org 패키지 저장소
```

#### I1. 에이전시 ↔ 고객사 데이터 흐름의 방향
| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | **에이전시 → 고객사가 기본**. 고객사 → 에이전시는 동의된 가명 데이터뿐 | 고객사 정보 경계가 구조로 지켜진다 · 업데이트 결정권이 고객사에 남는다 | 에이전시는 고객사 상태를 요약으로만 안다 |
| ⓑ | 에이전시가 고객사 설치본을 원격 조작(업데이트 · 진단) | 지원이 빠르다 | 고객사로 들어가는 원격 권한 · 고객사 정보 유입 |
- **채택:** ⓐ
- **선택 근거:** 결정 30(에이전시 = 내보내는 쪽) · 결정 31(업데이트 결정권은 고객사 — M28 범위 축소: 원격 조작 불필요) · 결정 37 · 38
- **기각 이유:** ⓑ — 결정 31 이 원격 조작을 불필요로 닫았고 결정 37 경계와 충돌
- **반증 조건:** 관리형 지원에서 원격 진단 없이는 해결 못 하는 장애가 반복되면 고객 동의 하의 일시 경로를 다시 본다
- **부작용:** 에이전시는 가명 요약 이상의 원인 정보를 못 본다 — 지원은 FDE 채널(I9) 질문 · 답으로 → §5 K2 (버전 분산 지원 부담)

#### I2. 에이전시 수신 서버 위치 (A3)
| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | 창업자 머신 + Tunnel | 추가 비용 없음 · PoC 엔진 호스팅(M33 ⓐ)과 같은 구성 | 창업자 머신이 꺼지면 수신이 멈춘다 |
| ⓑ | 서버리스(Cloudflare Workers + D1) | 설치본 수와 무관하게 받는다 · 운영할 서버가 없다 | 제공사 종속 · 한도 |
| ⓒ | 작은 VM | 무엇이든 돌릴 수 있다 | OS · 패치 · 가동을 직접 운영 |
- **채택:** ⓑ — **A3 확정에 따른다**
- **선택 근거:** A3 권장안 근거(창업자 머신 상태와 무관 · 받는 데이터가 가명 메타데이터뿐이라 단순 저장으로 충분)
- **기각 이유:** ⓐ — 고객사 설치본이 늘어도 창업자 머신 상태와 무관해야 한다(A3) · ⓒ — 단순 저장에 서버 운영 부담이 과하다
- **반증 조건:** 수신 처리에 Workers 가 돌리지 못하는 일(예: 받는 쪽 비식별 재검사가 Python 엔진 의존)이 필요해지면 ⓒ 를 다시 본다 — Workers 는 Python 엔진을 직접 돌리지 못한다(ideation §0.0 14차 기술 제약)
- **부작용:** Cloudflare 종속 · 한도 → §5 K7 · 받는 쪽 재검사(I8)를 Workers 에서 돌릴 수 있는 형태로 써야 한다

#### I3. 배포물 · 설치 스크립트 호스팅 (A4)
| 후보 | 방식 | 장점 | 단점 · 비용 |
|---|---|---|---|
| ⓐ | GitHub Releases 만 | 운영 부담 없음 | 설치 스크립트 주소가 저장소 경로에 묶인다 |
| ⓑ | 자체 도메인만 | 주소 통제 | 배포물 저장 · 전송을 직접 운영 |
| ⓒ | 배포물은 GitHub Releases, 설치 스크립트는 자체 도메인(버전 핀 + SHA-256) | 스크립트 주소는 고정 · 배포물만 교체 | 두 곳에 의존 |
- **채택:** ⓒ — **A4 확정에 따른다**
- **선택 근거:** A4 권장안 · uv 선례(자체 도메인 스크립트 + URL 버전 고정 + GitHub 릴리스 페이지 병행, distribution-channels §G.2) · §L.1 공통 필수(버전 핀 + 무결성 해시)
- **기각 이유:** ⓐ — 스크립트 주소를 바꾸지 않고 배포물만 교체하기 어렵다 · ⓑ — 배포물 호스팅까지 직접 운영할 이유가 없다
- **반증 조건:** GitHub Releases 의 배포 제약(용량 · 속도 · 접근)이 설치를 막는 것이 확인되면 ⓑ 를 다시 본다
- **부작용:** GitHub 장애 · 정책 변경 시 설치 불가 → §5 K13 · 스크립트 도메인 운영(HSTS, I12)

#### I5. 엔진 버전 선택 방식

|---|---|---|---|
| ⓐ | 엔진 버전 런처 — `solosquad` 는 리포의 `core/engine.lock` 을 읽어 해당 버전 엔진으로 실행. 엔진은 보관소에 버전별로 나란히. `prune` 은 어떤 리포도 안 쓰는 버전만 삭제 | 같은 컴퓨터에서 고객사마다 다른 엔진(C4) · 직전 엔진 즉시 복귀(C3) | 디스크에 엔진이 여러 벌 |
| ⓑ | 전역 단일 엔진을 제자리 교체 | 디스크 · 구조 단순 | C4 불가 · 복귀하려면 재설치 |
- **채택:** ⓐ
- **선택 근거:** M15(엔진은 버전별로 나란히 설치) · 결정 31(적용 · 보류 · 건너뛰기는 고객사마다) · C3 · C4
- **기각 이유:** ⓑ — 한 컴퓨터의 고객사 A · B 가 다른 결정을 할 수 없다
- **반증 조건:** 검토한 반증 없음 — C4 가 요구사항인 한 유지
- **부작용:** 엔진 보관소 디스크 누적 → §5 K6 · `prune` 이 다른 리포의 lock 을 모두 찾아야 한다 [보강 필요: 보관소가 리포 목록을 아는 방식]
