## 4. 인수 조건

- Given 고객사 A · B 가 각자 배포됨 / When A 계정으로 로그인 / Then A 의 회사만 보이고 B 의 도메인 · 데이터에는 A 계정으로 접근할 수 없다
- Given 로그인하지 않은 방문자 / When 고객사 도메인 접속 / Then 로그인 화면 외에는 어떤 API 도 응답하지 않는다
- Given org 2개(테슬라 · 스페이스X) 계정을 둘 다 가진 사람 / When 계정 전환 / Then 전환한 org 의 사무실만 보인다
- Given 내부망 유형 사무실 / When 사내망 밖에서 접속 / Then 로그인이 맞아도 사무실 검증에서 막히고 *사내망에서만 열립니다* 안내가 뜬다
- Given 팀 3개(재무 · 소싱 · 마케팅) / When 사무실 화면 / Then 팀마다 소속 에이전트와 지금 하는 과제가 보인다
- Given 과제가 승인 대기로 멈춤 / When 사장님이 웹에서 승인 / Then 그 지점부터 이어지고 승인자 · 시각이 기록된다
- Given 자리를 비운 8시간 동안 과제 3개 완료 / When 접속 / Then 첫 화면에 3개의 보고와 비용 합계가 보인다
- Given 실행 정책이 `외부 API 금지` 인 사무실 / When 라우팅 / Then 외부 API 키가 있어도 사내 · 로컬 모델로만 간다
- Given 연결 1개 월 예산 80% / When Chief 가 감지 / Then 웹에 경고와 제안(다른 연결 · 예산 조정)이 뜬다
- Given 창업자가 고객사 솔루션 리포에 push 후 재배포 / When 인스턴스 재시작 / Then 진행 중 과제는 이어지고 데이터 폴더는 유지된다
- Given 웹 서버 재시작 / When 다시 접속 / Then 로그인 세션은 만료 전까지 유지되고 대화 · 과제가 그대로다

## 5. 구현 방법

### 5.1 아키텍처 · 구조 (system-architect)

```
 브라우저 ──https──▶ Cloudflare (Access: 이메일 OTP · 허용 목록)
                         │ Tunnel (고객사별 호스트명 → localhost 포트)
                         ▼
 창업자 상시 머신 ─ 인스턴스(사무실 1개) ───────────────────────────────
   ASGI 앱 (Starlette · uvicorn, W2)
     /            → web/ 빌드 정적 파일 (W5: 같은 origin)
     /api/*       → 인증 미들웨어(세션 쿠키) → 기존 운영 층 API 를 감싼 라우터
     /api/events  → SSE (사무실 · 과제 · 승인 실시간)
   RunManager · 회사 그래프 · 라우터 (v2.0.0 그대로)
   데이터 폴더: org/accounts.sqlite (W6) · 사무실/state · runs · ledger · secrets
```

- **경계 원칙** — 웹은 v2.0.0 의 운영 층 API(threads · runs · state · resume · ledger · events)만 쓴다. **코어를 고치지 않고 웹이 붙는 것**이 이 버전의 구조 검증이다. 인증 · 세션 · 정적 파일은 표면 층에 새로 생기고 코어는 모른다.
- **고객사 격리** — 고객사(솔루션 리포)마다 인스턴스 · 포트 · 호스트명 · 데이터 폴더가 다르다. 한 머신에 여러 고객사가 떠도 Tunnel 라우팅으로만 이어진다.
- **대안** — ⓐ 같은 origin 서빙(채택) ⓑ Pages + 교차 origin(쿠키 SameSite · CORS · CSRF 설계 부담). 반증: 웹 빌드 배포 주기가 엔진과 크게 달라지면 ⓑ.

### 5.2 설계 (frontend · backend)

- **웹(frontend)** — React + Vite + TypeScript(프로토타입과 동일). 상태: 서버 상태는 API 질의 캐시(TanStack Query 류), 실시간은 SSE 구독으로 캐시 무효화. 화면은 프로토타입의 Arc 레이아웃 · 사무실 · 대화 · 승인 · 워크플로 · 비용을 결선 순서대로.
- **계약(backend ↔ frontend)** — 코어의 응답 모델을 pydantic 으로 정의 → JSON Schema → TS 타입 생성(빌드 단계). 손으로 쓴 TS 타입 금지 — 스키마가 단일 출처(결정 10).
- **API(backend)** — 기존 `server.py` 라우트를 Starlette 라우터로 옮기고 인증 미들웨어를 앞에 둔다. 승인은 `POST /api/threads/{id}/resume` — 승인자 · 시각을 run 기록에 남긴다.
- **오류 · 재시도** — SSE 끊김은 클라이언트가 지수 백오프로 재연결하고 마지막 이벤트 시각 이후를 다시 받는다(`Last-Event-ID`).

### 5.3 데이터 (data-engineer)

| 저장 | 위치 | 스키마 요지 | 보존 |
|---|---|---|---|
| 계정 | `data/<고객>/<org>/accounts.sqlite` | users(id, email, pw_hash(scrypt), role, created) · sessions(id, user_id, expires, ip, ua) | 계정 삭제 시까지 · 세션 14일 |
| 승인 기록 | `runs.sqlite` runs 확장 | approver_id · approved_at | 영구 |
| 보고 기준점 | `accounts.sqlite` | user_last_seen(user_id, ts) — "지난 접속 이후" 계산 | 영구 |

- 비밀번호는 표준 라이브러리 `hashlib.scrypt`(추가 의존 없음). 세션 id 는 256비트 난수, 쿠키 `HttpOnly · Secure · SameSite=Lax`.
- 고객 데이터는 고객사 머신(=창업자 머신의 그 고객사 데이터 폴더) 밖으로 나가지 않는다. Cloudflare 는 전송만 한다.

### 5.4 보안 · 권한 (security)

- 1차 문 = Cloudflare Access(허용 이메일) · 2차 = 앱 세션(W3). 로그인 전에는 `/api/*` 전부 401.
- 사무실 검증 = 계정의 사무실 권한 + 접속 경로(클라우드: 인터넷 허용 · 내부망: 사내망 대역/VPN · 로컬: 루프백).
- CSRF: 상태를 바꾸는 요청은 세션별 토큰 헤더 필수. 보안 헤더(CSP · HSTS · frame-ancestors) 기본.
- 감사: 로그인 · 승인 · 연결 변경은 기록. API 키는 저장 후 다시 보여주지 않는다(끝 4자리만).

## 7. 검증

- 자동: Python(API · 인증 · 사무실 검증) + 웹 테스트 · 린트 + **계약 테스트**(생성된 TS 타입 = 서버 스키마)
- 보안: 로그인 전 전 API 401 · CSRF 없는 변경 요청 거부 · 다른 고객사 호스트로 세션 재사용 불가
- **PoC 리허설** — 가상 고객사 '모아 리빙' 으로 로컬 작업 → 프라이빗 리포 → Cloudflare 배포 → API 키 연결 → 웹 계정 발급 → 7일 구동 → 승인 10회 · 재배포 1회. 통과: 수동 DB · 파일 조작 0 · 재배포 중 과제 유실 0
- AI 부록(R6): 에이전트 답변 품질은 이 버전에서 판정하지 않는다(v2.2.0 org 패키지 Eval). 이 버전의 AI 검증은 "실제 AI 응답이 웹까지 끝까지 흐르는가"(실기 스모크).
