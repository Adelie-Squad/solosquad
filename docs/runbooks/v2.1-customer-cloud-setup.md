## 0. 고객 프로필 받기 (결정 50)

구축 전에 고객에게 6가지를 받는다. 고정된 답은 없고, 고객 상황에 맞춘다.

| 항목 | 예 | 결정 기준 |
|---|---|---|
| 서버 위치(나라) | KR | Claude · OpenAI 를 쓰면 지원 지역(서울 · 도쿄 · 싱가포르 …), 중국 모델만이면 홍콩 · 본토 가능(결정 45) |
| 클라우드 제공사 · 리전 | AWS `ap-northeast-2` | 고객이 이미 쓰는 곳 우선 |
| 에이전시 접근 방식 | 고객 계정의 FDE 전용 IAM 역할 | 비밀번호 공유 금지 · 인계 후 회수 여부 합의 |
| 모델 계정 보유 법인 | 한국 법인 · 중국 법인 | 법인마다 설립국 · 지배회사 본사 소재국 |
| 언어 | ko (기본) · en · zh-CN | 직원 구성 |
| 개인정보 규정 · 검토 주체 | PIPA · PIPL / 고객 법무팀 | 사람 이름이 아니라 역할로 |

**자격 미리 보기:** 지배회사 본사가 중국 · 홍콩 · 마카오인 법인 명의 계정이나, 그 지역의 서버에서는 Anthropic · OpenAI 를 연결할 수 없다. 이런 업무는 Qwen · DeepSeek · Kimi · GLM 등 지원 지역 모델로 돌린다. 이 판정은 기록된 정책을 적용하는 것이지 법률 판단이 아니다. 최종 확인은 고객과 고객의 법률 자문이 한다.

## 1. 클라우드 준비 (고객 계정)

1. **VM 1대**를 프로필의 리전에 만든다. 사양 `[보강 필요: 최소 vCPU · 메모리 — 첫 고객 실측 후 확정]`, OS 는 Ubuntu LTS 또는 macOS 서버.
2. 디스크 암호화를 켠다(클라우드 기본 기능).
3. 방화벽은 **443(HTTPS)과 관리용 SSH 만** 연다. SSH 는 FDE 접근 경로로 제한한다.
4. 청구서가 고객 명의로 나오는지 확인한다(결정 47 S6).

## 2. 도메인 · TLS

패스키와 보안 쿠키 때문에 **도메인 + TLS 가 필수**다. IP 만으로는 로그인할 수 없다(결정 47 S4).

1. 고객 도메인(또는 하위 도메인, 예: `ai.<고객도메인>`)의 A 레코드를 VM 공인 IP 로 연결한다. 고객 도메인이 없으면 SoloSquad 하위 도메인을 임시로 쓰고, 인계할 때 고객 도메인으로 옮기도록 안내한다.
2. 리버스 프록시로 **Caddy**(자동 TLS)를 설치하고, 엔진(127.0.0.1)으로 넘긴다.

```caddyfile
ai.example.co.kr {
    reverse_proxy 127.0.0.1:7420
}
```

Caddy 는 `X-Forwarded-For` 를 붙인다. 엔진은 **같은 VM(127.0.0.1)에서 온 요청의 이 헤더만** 믿고 접속 정책(IP 허용)을 판정한다. 엔진 포트(7420)는 외부에 열지 않는다.

## 3. 엔진 설치 (결정 48 — v2.3 curl/irm 전까지는 git clone)

```bash
git clone <SoloSquad 리포> ~/solosquad && cd ~/solosquad/python && uv sync
uv run solosquad init ~/clients/<고객> --org <org> \
  --server-country KR --cloud aws --region ap-northeast-2 \
  --cloud-access "FDE IAM role" \
  --entity "<id>=<법인명>:<설립국>[:<지배회사 국가>]" \
  --language ko --privacy-regime PIPA --privacy-regime PIPL \
  --privacy-reviewer "고객 법무팀"
uv run solosquad profile show -s ~/clients/<고객>       # 체크리스트가 모두 ✓ 인지
```

고객 솔루션 디렉터리(`~/clients/<고객>`)는 **고객의 비공개 git 리포**로 관리한다. 데이터(`~/.solosquad/v2/data/…`)는 git 밖이다.

## 4. 사람 · 연결 · 정책

```bash
S=~/clients/<고객>
uv run solosquad accounts create-owner <대표 아이디> -s $S   # 대표 첫 계정 + OTP 등록(대표가 직접)
uv run solosquad connections add <id> --kind api_key --harness lite \
  --provider anthropic --models claude-sonnet --secret-env ANTHROPIC_API_KEY \
  --entity <보유 법인 id> -s $S                             # 자격이 안 되면 여기서 거부된다
uv run solosquad connections set-secret <id> -s $S          # 키는 데이터 폴더 비밀 저장소로
uv run solosquad workflows add monthly-pnl -s $S            # 첫 워크플로(W14)
uv run solosquad validate -s $S && uv run solosquad doctor -s $S
```

- **비밀 저장소는 암호화된다(I35).** 키는 `~/.solosquad/v2/keys/secrets.key` 에 처음 저장할 때 생기고, 데이터 폴더 · 백업 · 스냅샷에는 들어가지 않는다. 그래서 **키 사본을 고객의 비밀 관리 서비스(AWS Secrets Manager · NCP Secret Manager · 비밀번호 관리자)에 따로 보관**해야 한다. 키를 잃으면 모델 · 버킷 키를 다시 넣어야 한다. 키를 디스크에 두지 않으려면 서비스 환경에 `SOLOSQUAD_SECRET_KEY` 를 주입한다. `doctor` 가 키 위치를 보여준다.
- 직원 계정은 대표가 웹에서 발급한다. 직원은 첫 로그인 때 OTP 를 등록한다.
- 직원의 **팀 소속과 직함**은 대표가 조직도 화면에서 정한다. 팀 승인(결정 51)의 근거가 된다.
- 승인 등급은 권고값(구매 · 결제 · 송금 · 삭제 · 권한/접속 변경 · 연결 추가 = 대표 승인)으로 시작한다. 고객이 바꾸면 웹에 "권고와 다름"으로 표시되고 감사 기록이 남는다.
- 접속 정책의 기본값은 인터넷 + 로그인(결정 41)이다. 사무실만 쓰게 하려면 대표가 설정 화면에서 IP 허용 목록을 넣는다. 자기 주소가 빠지면 저장 전에 경고가 뜬다.

## 5. 상시 구동

```bash
uv run solosquad service install -s $S      # 재부팅 후 자동 시작, 죽으면 재시작
uv run solosquad status -s $S
```

Linux VM 에서는 `service install` 이 `loginctl enable-linger` 를 먼저 실행해, 아무도 로그인하지 않은 상태에서도 부팅 때 엔진이 켜진다(배포판 정책이 막으면 `sudo loginctl enable-linger <사용자>`).

`serve` 는 매일 보존 정리(업무 기록 3년 · 업로드 90일 · 감사 1년, `workspace.yaml` `retention:` 로 변경)와 스냅샷을 돈다.

## 6. 스냅샷 · 복원 리허설 (결정 54)

1. 고객 계정에 **스냅샷 전용 버킷**을 같은 나라에 만든다(공개 접근 차단 · 서버 측 암호화).
2. **그 버킷만** 읽고 쓰고 지울 수 있는 전용 키를 만든다. 예: AWS IAM 정책에서 `s3:PutObject` · `s3:GetObject` · `s3:DeleteObject` · `s3:ListBucket` 을 그 버킷 ARN 으로 한정한다.
3. 등록하고 바로 한 번 돌린다.

```bash
uv run solosquad snapshot set --type s3 --endpoint https://s3.ap-northeast-2.amazonaws.com \
  --region ap-northeast-2 --bucket <버킷> --prefix solosquad -s $S   # 키는 입력 프롬프트로
uv run solosquad snapshot run -s $S
```

4. **복원 리허설은 인계 전 필수다(K26).** 엔진을 멈추고 복원한 뒤 다시 켜서 데이터가 맞는지 본다.

```bash
uv run solosquad service uninstall -s $S
uv run solosquad snapshot restore -s $S          # 가장 최근 것, 체크섬 확인 후 교체
uv run solosquad service install -s $S
```

복원은 체크섬이 다른 파일을 거부하고, 엔진이 돌고 있으면 실행하지 않는다. 기존 파일은 `*.before-restore` 로 남긴다.

## 7. 인계 체크리스트

- [ ] 클라우드 · 도메인 · 버킷 · 모델 계정 · 청구가 모두 **고객 명의**다
- [ ] 대표가 웹으로 로그인하고 OTP 가 등록돼 있다. 대표가 휴대폰을 잃었을 때의 복구 절차를 안내했다: 서버에 접속할 수 있는 사람(FDE 또는 고객 IT 담당)이 `solosquad accounts reset-totp <대표>` · `solosquad accounts reset-passkeys <대표>` → 대표는 비밀번호로 로그인해 새 기기를 등록한다
- [ ] 비밀 저장소 키 사본(`keys/secrets.key`)을 고객 비밀 관리 서비스에 보관했다
- [ ] `solosquad profile show` 의 체크리스트가 모두 ✓ 다
- [ ] `solosquad validate` 오류 0 · `doctor` 실패 0
- [ ] 첫 워크플로(월 손익표)를 고객 원장으로 한 번 끝까지 돌렸다(업로드 → 확인 → 요약)
- [ ] 스냅샷이 버킷에 쌓이고, **복원 리허설을 했다**
- [ ] 접속 정책 · 승인 등급이 고객과 합의한 값이다
- [ ] 개인정보 규정 검토 결과를 고객 검토 주체가 확인했다(결정 50 · K23)
- [ ] 에이전시 접근(IAM 역할)을 회수할지 유지할지 정해 기록했다
- [ ] 월 비용(클라우드 · 모델)을 고객에게 보여줬다(결정 47 S6)

## 8. 정기 점검 (관리형 기간)

- 매주: `doctor` · 승인 대기 · 실패한 실행 · 예산 경고(웹 첫 화면)
- 매달: 스냅샷이 30일치 쌓였는지 · 복원 리허설 1회
- 엔진 업데이트: 업데이트 전에 `solosquad backup` 을 한 번 뜬다. 업데이트 때 스키마가 바뀌면 엔진이 적용 전에 스냅샷을 자동으로 남긴다(결정 54).
